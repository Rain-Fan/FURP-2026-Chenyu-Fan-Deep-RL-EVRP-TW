# Week 5 Track B Consolidation Design

## Purpose

Week 5 will consolidate the existing EVRP-TW experiment pipeline rather than
introduce a new routing method. The work will verify that the Week 4 controlled
comparison can be reproduced locally under its documented configuration, then
package the evidence and limitations in a concise project checkpoint.

## Scope

The work uses the existing Week 4 experiment runner and its three methods:

- `A_due_time_priority`;
- `B_nearest_customer`;
- `C_composite_score` with feasibility-aware 2-opt.

The experiment configuration remains fixed at the runner's documented defaults.
No external dataset, downloaded result, or manually invented measurement will be
introduced. All Week 5 result files will be generated by local commands.

## Deliverables

1. A dedicated `src/experiments/week5/` verification entry point that runs the
   Week 4 comparison twice with the same explicit seed and stores each run in a
   separate output directory.
2. A deterministic-stability check that compares the two locally generated CSV
   result tables, excluding measured runtime, and reports whether all
   deterministic metrics agree. It will preserve the raw run logs and the
   environment details used for the verification.
3. A short Week 5 checkpoint note that states the current project status,
   cites the generated comparison evidence, names concrete limitations, and
   gives two next research tasks.
4. Updates to the weekly log and README that point collaborators to the exact
   reproduction command and evidence locations.

## Data Flow

`week5/run_reproducibility_check.py` will invoke the existing Week 4 runner
twice through the local Python interpreter. Each invocation writes its native
CSV, JSON, Markdown, PNG, and console log to a run-specific directory. The
Week 5 script reads both generated CSV tables, compares deterministic fields,
and writes a small Markdown/JSON verification summary plus environment
metadata. The checkpoint draws its factual table only from that summary and the
generated Week 5 result files.

## Correctness and Failure Handling

The verification exits non-zero if either Week 4 run fails, expected output
files are absent, or deterministic fields differ. Runtime is recorded but not
required to match because it is system-load dependent. The result summary must
explicitly distinguish deterministic reproducibility from runtime variation.

## Validation

Automated tests will cover the result-table comparison behavior: equal
deterministic rows pass despite runtime changes, while a changed feasibility or
objective value fails. The full local verification command will then be run to
produce the committed Week 5 evidence. Documentation links and generated file
paths will be checked after the run.

## Constraints

- Preserve the existing Week 1--4 artifacts and experiment semantics.
- Use only locally executed code and generated outputs as Week 5 evidence.
- State limitations plainly; do not claim a paper reproduction or universal
  performance improvement.
- Record the fifth-week meeting as attended, as confirmed by the project owner.
