## Discussion summary

### Final Report Writing Requirements
- The final report should be structured and evidence-based rather than only
  describing the code. It should clearly connect the research question,
  methods, experiments, numerical results, and conclusions.
- The main report structure should include the problem and motivation,
  baseline and improved methods, experimental setup, results, discussion and
  failure analysis, limitations, and conclusion.
- The experimental setup should record the datasets or generated instances,
  tested scales, hardware and software environment, parameters, stopping
  criteria, random seeds, and evaluation metrics. Any simplification of an
  existing method should be stated explicitly.
- Results should compare the baseline and improved method on common instances
  and report objective value, feasibility, time-window and battery violations,
  and runtime together. Summary tables and figures should appear in the report;
  raw logs should remain in separate supporting files or an appendix.
- The discussion should explain why an improvement works, whether the result is
  consistent across scales and stress profiles, what runtime trade-offs it
  introduces, and where the method still fails.

### Resolving Problems With the Innovation
- A useful innovation does not need to be a completely new algorithm. A focused
  and well-motivated improvement to an existing method is valuable when it is
  evaluated fairly and its contribution can be explained.
- When an innovation idea is unclear, begin with a concrete weakness or failure
  case in the current method and turn it into a testable question about
  feasibility, solution quality, runtime, or robustness.
- Use baseline and ablation comparisons to separate the effect of each added
  component. Claims of improvement should be supported by repeated experiments,
  not by a single favorable instance.
- Unsuccessful attempts should also be recorded when they reveal why an idea
  fails or which constraint prevents it from working.

### New Angles From Combining Existing Methods
- Use the current project components as a unified workflow: construct an
  initial EVRP-TW solution, check feasibility, apply repair or local-search
  operators, and then evaluate the final feasible solution.
- Possible entry points include using a repair operator after construction,
  applying intra-route and inter-route local search in sequence, selecting the
  best feasible result from multiple heuristics, or combining a future learning
  policy with classical feasibility checking and post-processing.
- For every combined workflow, explain what each component contributes, why the
  components are used in that order, which simpler baseline is used for
  comparison, and whether the combination improves feasibility, objective
  value, runtime, or robustness.
- The existing composite-score construction and inter-route local search provide
  a concrete foundation for the final report. The innovation should be presented
  as a motivated combination supported by controlled comparisons and failure
  analysis.
